Status update: revision-specific Kane generation and human review are now implemented in the app; see README.md for the current flow. The historical fixed-suite results below predate this change and do not establish coverage of the new workflow.

Previous milestone: working local MVP. The pricing engine, campaign persistence, real OpenAI interpretation, Kane runner, and backend activation gate are implemented. Kane's PRD use cases and six checkout scenarios were reviewed; the general suite passed four of six. A separate, reviewed read-only candidate suite passed six of six for Welcome 20, and the gate allowed activation only for that exact policy and evidence. ## Outcome

A merchant describes a promotion, confirms the AI's interpretation, verifies the candidate campaign in a real browser with Kane, and activates that exact version only when its required checks pass.

The demo must show a real checkout result, traceable evidence, and Kane output changing what the coding agent does. A genuine defect is useful evidence, not a mandatory or fabricated outcome.

## MVP boundaries

- One local demo store, four fixed products, USD, integer-cent prices.
- One campaign being edited at a time; one active campaign revision.
- Supported policy: percentage discount, inclusive minimum eligible subtotal, maximum discount, new-customer-only eligibility, and sale-item exclusion.
- Three screens: campaign editor, storefront/cart, verification results.
- A labeled demo customer selector supplies new/returning status; it is not production identity verification.
- OpenAI interprets the merchant request. Ordinary application code calculates prices.
- Confirmation is mandatory. Unsupported or ambiguous requests stay unconfirmed until clarified.
- No real payments, Shopify integration, accounts, voice, external store URLs, campaign stacking, shipping rules, taxes, or scheduling.

## Proposed implementation

Use TypeScript throughout: React with Vite for the UI and a small Node/Express backend. Use npm with a committed lockfile. Keep UI, backend, and runner in one repository and start them with one development command.

The backend holds the OpenAI credential, validates campaign data, calculates checkout totals, controls activation, and runs a local Kane worker. Keep the server bound to localhost for this unauthenticated demo. Store revisions and verification metadata in a small local JSON file with atomic writes and serialized mutations; retain Kane's evidence separately.

Use polling for run progress. Do not add WebSockets or a job service. Permit one Kane job at a time. Use fixed executable arguments and approved test paths; merchant input must never become a shell command.

Proposed layout:

```text
docs/                    plan, PRD, demo script
src/                     merchant UI and storefront
server/                  API, campaign storage, activation, Kane adapter
shared/                  schema and deterministic pricing functions
requirements/            approved campaign policy sources
.testmuai/tests/          tests generated by Kane assurance
artifacts/               curated submission evidence and manifest
```

Keep secrets, dependencies, local state, logs, and `.context/` out of Git. Never merge or manually edit Kane's context store. Preserve generated replayable tests and curate actual evidence for the submission.

## Policy decisions to encode in the PRD

- The threshold uses eligible merchandise subtotal before discount. When sale items are excluded, they neither receive a discount nor count toward the threshold.
- A subtotal equal to the minimum qualifies.
- A returning customer receives no discount when the policy is new-customer-only.
- Compute a single cart-level percentage discount on eligible subtotal, round half up to cents, then apply the cap. Never exceed eligible subtotal.
- Sale items still contribute to the amount payable.
- Customer status is explicit in the demo; never infer it from free text.
- Confirmed policy text and structured configuration are retained together. Kane's expected behavior comes from the reviewed policy, not the pricing function being tested.
- Changing approved rules produces a new revision requiring review and verification.

## Evidence and activation contract

Candidate states: draft, ready for verification, running, failed, unverified, verified. Activation is a separate pointer to a verified immutable revision.

Editing an active campaign creates a candidate revision. The existing active revision remains unchanged while that candidate is checked. The UI clearly distinguishes candidate preview from active-store behavior.

A verification record binds the approved policy, campaign configuration, required test manifest, catalog, and application build identity. Build identity must account for current source contents, not just the last Git commit when there are uncommitted changes. Exclude generated artifacts from the source fingerprint.

Activation is enforced by the backend. It requires every selected required check to complete successfully with matching evidence and matching version identities. A zero exit code alone, a partial run, a stale report, a missing result, a timeout, or a manually toggled UI flag cannot activate a campaign. Recheck version identities when the run finishes and at activation so changes during execution cannot authorize the wrong version.

Report the scope of verification accurately: passing selected checks does not prove every possible checkout behavior. Missing or changed policy coverage blocks verification until the required suite is reviewed and updated.

## Build order and exit conditions

### 1. Product contract and repository foundation

Write `docs/PRD.md` with the MVP, policy semantics, errors, revision behavior, activation requirements, and explicit non-goals. Prepare `.gitignore`, README, and an environment-variable example containing no secrets. Make the first implementation commit only when implementation begins within the event rules.

Exit: a single requirements source, no conflicting scope, and a clear local startup plan.

### 2. Prove the tool connection early

Check Node/npm, Kane version, authentication, browser availability, and credits using the Kane skill preflight. Scaffold a minimal working page. Ingest the PRD, inspect the proposed use-cases, review them with the user, generate a narrow initial design, and review that design before execution. Have Kane run the first available real UI flow as soon as the app supports it.

Exit: genuine Kane evidence from our local app, with a known completion signal and readable results. Do not postpone discovering runner problems until the app is polished.

### 3. Build the pricing core and storefront

Implement the validated policy schema, pricing function, fixed catalog, cart, customer selector, and visible total breakdown. Add focused deterministic unit checks for monetary invariants and policy calculations. These complement Kane's generated browser tests.

Exit: the storefront computes totals reliably from a manually configured candidate policy.

### 4. Add OpenAI and merchant confirmation

Add a server-only parse endpoint, validate the returned structure, and display the interpretation in editable fields beside the request. Handle unsupported rules, ambiguity, invalid values, network errors, and retry without silently saving or activating. Save only after explicit confirmation.

Exit: natural-language request to confirmed candidate to observable checkout works end to end.

### 5. Integrate browser verification and the activation gate

Connect the verification action to a backend job using Kane-generated and reviewed tests. Provide deterministic reset and isolated run state so replays do not inherit previous carts. Map real terminal results and evidence to the dashboard. Implement persistent run metadata, version checks, failure handling, and backend activation enforcement. Prevent nested verification runs when testing the LaunchGate interface itself.

Exit: a completed required suite can authorize its exact candidate; failed, stale, incomplete, or unknown results cannot. A restart does not invent or discard verification authority.

### 6. Demonstrate evidence-driven repair

Inspect actual failures and distinguish application defects from test wording or infrastructure problems. Give the coding agent the evidence, correct application defects, and rerun the same relevant assertions. Preserve before/after evidence and the source change. Do not weaken assertions to manufacture a pass. If no genuine defect occurs, demonstrate verified behavior and disclose remaining coverage instead.

Exit: an explainable connection between Kane's result and the agent's next action, backed by real artifacts.

### 7. Requirement change and Maintain

After the core flow is reliable, revise one approved rule, such as the minimum eligible subtotal. Immediately invalidate candidate verification. Use Kane Maintain to reconcile the changed source, review changes, generate or evolve affected tests as required, then run them against the updated application. Do not present reconciliation alone as successful verification.

Exit: the revised campaign has its own current evidence; the old report cannot authorize it.

### 8. Freeze, rehearse, and submit

Complete a full local rehearsal, refresh only the checks affected by final changes, record a backup demo, and prepare a concise evidence manifest. Bundle the PRD, OpenAI explanation, actual Kane reports, coverage including gaps, repair history if available, and setup instructions. Verify the event's current submission destination: the public event site previously specified the team hub while earlier planning material specified Devpost.

Exit: complete submission and a three-minute demo with evidence accessible in one click.

## Kane workflow

Follow the installed CLI version and skill reference rather than assuming command syntax. The intended order is ingest/extract, use-case review, design, design review, initial authoring/execution, replay, and coverage. Maintain follows a changed source.

Tests and scenarios are generated through Kane assurance, not handwritten. Reviews are checkpoints on concrete generated material; they are not extra approvals before ordinary reversible implementation work. Serialize context-store writes. Parse command-specific terminal events as well as process exit codes; intermediate step completion is not suite completion.

Develop two verification scopes: the candidate promotion's checkout behavior, and LaunchGate's own confirmation, revision, result, and activation behavior. The demo verification action runs the checkout scope; do not recursively invoke itself.
